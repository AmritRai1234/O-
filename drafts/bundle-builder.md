# O- Bundle — Builder Draft

**Persona:** Pragmatic Builder
**Approach:** "go:embed Generation" — The Boring Baseline That Ships Today
**Bias:** Working code > perfect code. Call out Architect over-engineering. Veto abstractions without a second concrete use case.

---

## Core Philosophy

The CEO said "Bun bundles your assets for you, Go makes you wire go:embed by hand." The fix is NOT a runtime asset loader, a zip-payload post-processor, or a build-tag matrix — it's one generated Go file. `go:embed` is already production-grade, maintained by the Go team, proven in thousands of projects (including this one: `internal/scaffold/templates/` is already embedded via `//go:embed`). The job of `o- bundle` is to WRITE that `//go:embed` file for you, so you never type one by hand again.

```
User workflow:
  o-.yaml                    →  bundle.include: ["templates/**", "config/*.yaml"]
  o- bundle                  →  resolves globs → generates o-bundle.gen.go
                                 → imports o-embedded (embed.FS) → go build
  user's main.go             →  o-embedded.FS.ReadFile("templates/index.html")
```

**Mechanism decision: go:embed generation, NOT zip payload.**
- Zip payload requires a runtime reader + post-build binary mangling. It breaks `go build`, `go install`, `go run`, and any tool that expects a standard Go binary. It needs a second concrete use case — CEO already vetoed WASM, remote registries, and plugin loaders for this epic. Without a second consumer, zip payload is pure over-engineering.
- Build-tag asset dirs complicate the build matrix (with-assets vs without-assets binary variants) and confuse users. No second use case for that dimension either.
- go:embed generation: zero runtime cost, zero new dependencies, works with every Go tool, deterministic by construction.

## Design

### Manifest surface — aggressively minimal

Add ONE new section to the Manifest struct:

```yaml
# o-.yaml
bundle:
  include:
    - "templates/**"
    - "config/*.yaml"
    - "assets/images/**"
```

**What I would cut if the Architect proposes it:**
| Proposed field | Ruling |
|---|---|
| `bundle.prefix` | Cut. The user writes relative globs. `go:embed` preserves directory structure. No prefix abstraction needed until a second use case proves it. |
| `bundle.output` | Cut. Generated file path is deterministic (`o-bundle.gen.go`). Users who need to rename it can rename it — this is a config knob with zero value. |
| `bundle.strip` | Cut. Path prefix stripping is a runtime concern, not a build concern. Users write `templates/index.html` in their ReadFile call. If it hurts, add a helper later. |
| `bundle.exclude` | Cut. The glob patterns handle exclusion (`assets/**/*.go` for example). Adding exclude is a second mechanism for the same job. |
| `bundle.compression` | Cut. go:embed stores bytes as-is. Compression is the linker's job (if any). This is a premature optimization. |

MINIMUM: `bundle.include` — a list of glob strings. That's it. One new field.

### Generated file (`o-bundle.gen.go`)

```
// Code generated by o- bundle. DO NOT EDIT.
package main  // or the module's main package

import "embed"

//go:embed templates
//go:embed config
//go:embed assets/images
var Bundled embed.FS
```

The bundler:
1. Reads manifest, resolves `bundle.include` globs against project root
2. Groups matched files by their top-level directory (the first path component)
3. Emits one `//go:embed` directive per unique top-level directory
4. Emits `var _ embed.FS` with an exported name users can reference

Why group by top-level directory? Because `//go:embed` accepts a directory and embeds its entire subtree. If the user says `templates/**`, that's one directive: `//go:embed templates`. Fewer directives = simpler generated file = smaller surface for bugs. The glob resolution step is just a sanity check that files actually exist (fail fast with a clear error if a glob matches nothing).

### Determinism (Quality #1)

- Glob results sorted by `filepath.Walk` order — filesystem-dependent on some OSes. Fix: sort the emitted directive list AND the file-level listing by `path.Clean` + lexicographic order before emitting.
- Generated file header includes a sha256 comment so the build cache key materializes it correctly: `// sha256: <hash of resolved file set>`.
- The existing Builder's `sourceHash()` already walks `.go`, `.yaml`, `.html`, `.tmpl`, `.json`, `.mod`, `.sum` files. Add the generated file's extension `.gen.go` so asset changes trigger a cache miss.

## Implementation Plan — Fastest Path to Demo

### Step 1: Manifest change (one file, ~10 lines)

```go
// internal/manifest/manifest.go
type Bundle struct {
    Include []string `yaml:"include"`
}
type Manifest struct {
    ...
    Bundle Bundle `yaml:"bundle"`
}
```

### Step 2: New package `internal/bundler/` (one file, ~80 lines)

```go
package bundler

// Generate(dir string, includes []string) error
// Steps:
//   1. Resolve each glob against dir
//   2. Group by top-level directory
//   3. Fail if any glob matches zero files (fail fast, not silent skip)
//   4. Emit o-bundle.gen.go with sorted //go:embed directives + var Bundled embed.FS
//   5. Write sha256 comment fo build cache keying
```

### Step 3: CLI command `o- bundle` (~20 lines, same pattern as build.go)

```go
func NewBundleCmd() *cobra.Command {
    return &cobra.Command{
        Use:   "bundle",
        Short: "Embed declared assets into the binary",
        RunE: func(cmd *cobra.Command, args []string) error {
            // 1. Load manifest
            // 2. Call bundler.Generate(dir, m.Bundle.Include)
            // 3. Call builder.Build() — picks up o-bundle.gen.go naturally
        },
    }
}
```

### Step 4: Wire into main.go (1 line)

```go
root.AddCommand(cli.NewBundleCmd())
```

### Step 5: Demo

```
$ o- new demo
$ echo '<h1>{{.Name}}</h1>' > demo/templates/index.html
$ o- bundle   # generates o-bundle.gen.go, then go build
$ ./demo      # reads from embedded FS — no external templates/ directory needed
$ o- run      # live-reload also works because generated file is in the build
```

Total new code: < 200 lines. Zero new dependencies. Zero runtime changes.

## Risks — What a Security Reviewer and Performance Skeptic Would Attack

### Security Reviewer's attacks

1. **Glob injection / path traversal.** A malicious `o-.yaml` with `bundle.include: ["../../etc/**"]` could cause the generated file to embed system files. Mitigation: bundler.Resolve() must reject globs whose resolved paths escape the project root. Use `filepath.EvalSymlinks` on the project root AND each matched file root, reject if the result is not within the project root. Already have this pattern in `internal/scaffold/safePath`.

2. **Generated file committed + stale.** If a developer commits `o-bundle.gen.go`, edits `o-.yaml` but forgets to re-run `o- bundle`, the binary ships stale assets. Mitigation: `o- build` should detect that `bundle.include` is non-empty and the generated file is absent or stale (hash mismatch), and either warn or auto-run `o- bundle`. Architect might propose a "pre-build hook" — I say: make `o- build` check and auto-generate as a silent operation. The developer never thinks about it.

3. **Large asset denial-of-service.** A glob like `**/*` in a repo with 100K files produces a Go file with enormous `//go:embed` directives, bloating the binary and the build. Mitigation: reasonable cap (e.g., 10K files or 100MB total), documented in the error message. The manifest has a 1MB cap already — this is the same principle.

### Performance Skeptic's attacks

1. **Binary size bloat.** Embedding a 50MB `node_modules` directory (because the glob was `**/*` instead of `static/**/*`) makes the binary unusable. Mitigation: same cap as above, PLUS a summary output after generation ("o- bundle: embedded 142 files (3.2 MB)") so the developer has visibility. This is a UX issue, not an architecture issue — go:embed already stores the data efficiently.

2. **Cache invalidation.** The existing `sourceHash()` in builder.go walks `.go`, `.yaml`, `.json`, `.html`, `.tmpl`, `.mod`, `.sum`. It does NOT walk `.css`, `.js`, `.png`, `.svg` — the very file types `bundle.include` targets. If you add a CSS file, `sourceHash` stays the same, and the cache returns a stale binary. Mitigation: Add the resolved file list (or its combined sha256) to the cache key. The bundler already computes this hash for the generated file header — pass it to the builder and include it in `projectKey()`. About ~10 lines to plumb.

3. **Build latency.** Glob resolution + hash computation adds ~10-50ms, negligible compared to `go build`. Not a real concern, but the skeptic will point it out. Document the measurement.

## What I Veto (Calling Out the Architect Preemptively)

| Architect proposal | Why it's over-engineering |
|---|---|
| Runtime zip reader + post-build zip append | No second use case. CEO rejected WASM/plugins for this epic. A runtime reader is a whole new subsystem for zero benefit over go:embed. |
| Build-tag matrix (with-assets / without-assets) | When would a developer want TWO binaries? They want ONE binary that works. |
| `bundle.prefix` / `bundle.strip` / `bundle.exclude` / `bundle.compression` / `bundle.output` | Every field added to the manifest is a new contract, a new test, a new documentation burden. Prove it's needed with a real user story, not a hypothetical. |
| Globbing library dependency (e.g., `doublestar`) | `filepath.Glob` handles `**` on Go 1.24+ via `filepath.WalkDir`. stdlib is enough. If a glob edge case bites, fix with a simple recursive walk helper (50 lines) — no new dep. |
| Separate bundler cache layer | The existing builder cache + the hash of the resolved file list is sufficient. A second cache is another abstraction without a concrete second use case. |
| "o- bundle --watch" | CEO said simplicity (#4) constrains scope. Live-reload on asset changes during development is a nice-to-have, not a v0.2 requirement. Developer runs `o- bundle` when they change assets. |

## Summary

| Aspect | Decision |
|---|---|
| Mechanism | go:embed generation (one `o-bundle.gen.go` file) |
| Runtime cost | Zero. go:embed is compile-time. |
| Dependencies | Zero new. Uses `filepath.Glob`, `embed` (stdlib). |
| New code | ~200 lines |
| Demo path | `o- new demo → o- bundle → ./demo` — 2 hours |
| Top risk | Stale generated file → auto-check in `o- build` |
| Cache correctness | Include asset file list hash in `projectKey()` |
| Security | Reject globs escaping project root (safePath pattern) |
| Determinism | Sorted glob output, sha256 annotation in generated header |
